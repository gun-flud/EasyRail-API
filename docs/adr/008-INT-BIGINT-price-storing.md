# ADR 008: Зберігання фінансових даних у мінімальних одиницях валюти (Цілі числа / Cents) замість рядків (STRING)

**Статус:** Затверджено

**Дата:** Жовтень 2026

**Контекст:**  
У початковій концептуальній моделі та UI-макетах вартість квитка зберігалася як `STRING` (`"150.00 грн"`). Це заблокувало доменну математику: динамічні тарифи, коефіцієнти класів вагонів, розрахунок відрізків поїздки, агрегації (`SUM`, `AVG`) та утримання штрафів при поверненні. Виникла потреба обрати числовий тип даних, який гарантує 100% точність фінансових операцій.

**Розглянуті альтернативи:**  
1. **Збереження `STRING` із парсингом у коді:**  
   Помилкове лексикографічне сортування в SQL (`'100' < '50' === true`), неможливість накласти констрейнт $\text{CHECK (price > 0)}$ на рівні БД, постійний runtime-кастинг та втрата підтримки індексів.
2. **Числа з рухомою комою (`FLOAT` / `DOUBLE PRECISION`):**  
   Категорично неприпустимо у фінтеху через специфікацію IEEE 754: двійкові похибки округлення ($0.1 + 0.2 \ne 0.3$) накопичуються та руйнують фінансовий баланс при кожній тисячі транзакцій.
3. **Дробові числа фіксованої точності (`NUMERIC(10, 2)` / `DECIMAL`):**  
   Точний тип у PostgreSQL, проте в середовищі JavaScript/TypeScript вимагає важких сторонніх бібліотек або рядкової серіалізації, що створює ризик випадкового перетворення в `number` і втрати точності.
4. **Цілі числа в мінімальних неподільних одиницях (`INTEGER` / `BIGINT` у копійках):**  
   Збереження всіх сум у копійках ($100\text{ грн} = 10000$). Усі операції додавання, віднімання та множення на цілі коефіцієнти виконуються нативно й абсолютно точно.

**Прийняте рішення:**  
Повністю відмовитися від `STRING` та дробових типів. Усі ціни, тарифи, суми оплат та повернень зберігати виключно як цілі числа (**`INTEGER`**) у **копійках**. Будь-яке переведення у гривні та форматування валюти для користувача виконується виключно на стороні клієнта.

**Наслідки:**  
* **Позитивні:**  
  * Нульова ймовірність похибок округлення — абсолютна фінансова точність.
  * Висока продуктивність: цілочисельна арифметика виконується за 1 такт CPU без конвертацій.
  * Апаратний захист цілісності через констрейнт $\text{CHECK (price > 0)}$ та прозору Zod-валідацію (`z.number().int().positive()`).
* **Негативні:**  
  * Клієнт зобов'язаний самостійно ділити значення на 100 перед рендерингом (`45050` $\to$ `"450.50 ₴"`).
  * Операції процентного розрахунку (наприклад, штраф повернення $70\%$) вимагають явного визначення правил округлення (`Math.floor` або `Math.round`).
