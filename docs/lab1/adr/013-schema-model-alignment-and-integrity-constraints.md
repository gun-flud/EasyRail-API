# ADR 013: Узгодження концептуальної моделі зі схемою та захист цілісності даних

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Mermaid-модель і SQL-схема описують одну предметну область, тому розбіжність між назвами таблиць, полів, типами та значеннями enum призводить до помилок під час реалізації. Окремо база даних має гарантувати базові правила маршруту, розкладу, ціни та бронювання незалежно від перевірок бекенду.

**Прийняте рішення:**  
SQL-схема є джерелом істини для фізичних назв і обмежень. Концептуальна модель у `docs/lab1/model.mmd` повинна відображати ті самі таблиці, поля, зв'язки та enum-значення. Зміни схеми вважаються неповними, якщо відповідна модель не оновлена.

У схемі зберігаються такі обмеження цілісності:

- кожна сутність має UUID первинний ключ;
- email користувача, тип вагона, назва станції разом із містом та ідентифікатори платежів мають бути унікальними відповідно до схеми;
- номер вагона унікальний у межах маршруту, номер зупинки — у межах маршруту, станція — у межах маршруту, а номер місця — у межах типу вагона;
- ціни, множник тарифу, кількість місць, номер вагона, номер місця та номер зупинки мають бути додатними;
- `delay_minutes` і `arrival_offset_minutes` не можуть бути від'ємними;
- `departure_offset_minutes` не може бути меншим за `arrival_offset_minutes`;
- для квитка `from_stop_order` має бути меншим за `to_stop_order`, станції відправлення та призначення мають відрізнятися, а `arrival_time` має бути пізнішим за `departure_time`;
- усі зв'язки з довідниками та батьківськими сутностями реалізуються зовнішніми ключами; для станцій квитка видалення обмежене через `ON DELETE RESTRICT`;
- часові поля квитка та рейсу використовують `TIMESTAMPTZ`, а грошове поле `price` — цілі копійки (`INT`).

**Наслідки:**  
- **Позитивні:** Модель, міграція та реалізація використовують однаковий словник даних; помилки перейменування виявляються під час рев'ю моделі; база даних відхиляє некоректні маршрути, часові інтервали та дублікати.
- **Позитивні:** Обмеження є захистом другого рівня після валідації API та зберігають цілісність при імпорті, скриптах і прямих SQL-запитах.
- **Негативні:** Додавання або перейменування поля вимагає синхронної зміни SQL-схеми, Mermaid-моделі та пов'язаного коду. Частина бізнес-правил, зокрема перевірка перетину сегментів і ліміту активних холдів, потребує транзакційної логіки та індексів, а не лише наведених обмежень.
