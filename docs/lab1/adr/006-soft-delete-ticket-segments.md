# ADR 006: Відмова від Hard Delete на користь строгої скінченної машини станів (State Machine)

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Квитки, рейси та фінансові транзакції підлягають аудиту та юридичній звітності. Фізичне видалення рядків (`DELETE FROM ticket_segments`) призводить до втрати фінансової історії, ламає цілісність аналітики та унеможливлює розслідування збоїв.

**Розглянуті альтернативи:**  
1. **Фізичне видалення (`DELETE`):**  
   Звільняє простір у базі, проте знищує історію оплат, повернень і спроб бронювання.
2. **Класичний Soft Delete (поле `deleted_at`):**  
   Додавання прапорця `is_deleted` або `deleted_at`. Створює надмірну складність унікальних індексів і запитів (кожен `SELECT` змушений містити умову `WHERE deleted_at IS NULL`).
3. **Скінченна машина станів (State Machine через ENUM `ticket_status`):**  
   Рядок квитка ніколи не видаляється. Він змінює свій статус за суворим графом переходів:
   $$\text{HELD} \longrightarrow \text{PAID} \longrightarrow \text{CANCELLED}$$
   $$\text{HELD} \longrightarrow \text{EXPIRED}$$

**Прийняте рішення:**  
Заборонити прямий `DELETE` для сутностей квитків і рейсів. Впровадити **машину станів** на базі ENUM-типу `ticket_status` (`HELD`, `PAID`, `CANCELLED`, `EXPIRED`).

**Наслідки:**  
- **Позитивні:** Повна аудитопридатність системи. Можливість у будь-який момент відтворити історію будь-якого місця та зібрати статистику заповненості.
- **Негативні:** Збільшення обсягу таблиці `ticket_segments`, що вимагає часткових індексів (Partial Index `WHERE status = 'HELD'`), аби не індексувати старі неактивні записи.
