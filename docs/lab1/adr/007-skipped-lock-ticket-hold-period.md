# ADR 007: Очищення черг експірації за патерном `SKIP LOCKED` замість брокерів повідомлень

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Квитки зі статусом `HELD` мають діяти рівно 10 хвилин. Якщо користувач не оплатив замовлення, місце має автоматично повернутися у вільний продаж. Потрібен механізм фонового скасування, який не створює блокувань для реальних покупців.

**Розглянуті альтернативи:**  
1. **Зовнішній брокер з чергою відкладених повідомлень (RabbitMQ / BullMQ на Redis):**  
   Створює проблему подвійного запису (The Dual-Write Problem): стан у Redis/RabbitMQ може розійтися зі станом у базі даних, якщо під час публікації обірветься мережа.
2. **Наївний SQL-опитувач (`UPDATE ... WHERE hold_expires_at < NOW()`):**  
   Викликає блокування цілих сторінок таблиці (Lock Contention), через що користувачі, які паралельно купують квитки, зависають в очікуванні відпускання локів.
3. **Неблокуюча черга через патерн `FOR UPDATE SKIP LOCKED`:**  
   Воркер вибирає прострочені рядки, ігноруючи ті, які прямо зараз обробляються іншими транзакціями (наприклад, перебувають у процесі оплати).

**Прийняте рішення:**  
Реалізувати фоновий воркер скасування на рівні PostgreSQL за допомогою патерну **`FOR UPDATE SKIP LOCKED`**:
```sql
UPDATE ticket_segments
SET status = 'EXPIRED'
WHERE ticket_id IN (
  SELECT ticket_id FROM ticket_segments
  WHERE status = 'HELD' AND hold_expires_at < NOW()
  FOR UPDATE SKIP LOCKED
);
```

**Наслідки:**  
- **Позитивні:** Збереження принципу **Zero-Broker Architecture**. Нульовий вплив фонового процесу на швидкість оформлення покупок іншими клієнтами. Гарантія роботи навіть за наявності кількох паралельних інстансів воркера.
- **Негативні:** Воркер опитує базу з періодичністю (наприклад, раз на 30–60 секунд), тому місце звільняється не із субмілісекундною точністю, а з невеликою затримкою у межах одного інтервалу опитування, що є прийнятним для домену залізниці.
