# ADR 001: Моделювання топології маршрутів через порядкові номери зупинок (`stop_order`)

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Поїзд рухається залізничною мережею через послідовність станцій. Потрібно швидко визначати валідність напрямку руху пасажира (поїзд їде вперед, а не назад) та розраховувати тривалість і вартість без використання громіздких геоінформаційних (GIS) обчислень.

**Розглянуті альтернативи:**  
1. **Географічні координати та просторові запити (PostGIS):**  
   Зберігати `latitude/longitude` кожної станції та вираховувати відстані за формулою гаверсинуса. Занадто важкий стек, що не враховує реальну геометрію рейок та складність залізничних петель.
2. **Графові структури в пам'яті (Graph Database):**  
   Використання Neo4j для пошуку шляхів. Створює надмірне розшарування архітектури для простої лінійної послідовності станцій рейсу.
3. **Дискретні цілочисельні індекси послідовності (`stop_order`):**  
   Кожна зупинка маршруту отримує монотонно зростаючий цілочисельний порядковий номер: $1, 2, 3, \dots, N$.

**Прийняте рішення:**  
Описати топологію зв'язку маршруту зі станціями через проміжну таблицю `stops`, де кожна зупинка має атрибут **`stop_order INT NOT NULL`** із констрейнтом:
$$\text{CHECK (from\_stop\_order < to\_stop\_order)}$$

**Наслідки:**  
- **Позитивні:** Перевірка вектору руху перетворюється на елементарне математичне порівняння: $\text{order}_{\text{from}} < \text{order}_{\text{to}}$. Розрахунок вартості та перевірка конфліктів відрізків виконується на чистому B-Tree індексі без додаткових обчислень.
- **Негативні:** Неможливість прямого використання однієї таблиці для кільцевих маршрутів, де поїзд проходить одне й те саме місто двічі (вимагає створення окремих віртуальних записів зупинок із різними `stop_order`).
