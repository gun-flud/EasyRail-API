# ADR 010: Зберігання ролі облікового запису в `users`

**Статус:** Затверджено  
**Дата:** Жовтень 2026

**Контекст:**  
У системі є три типи облікових записів із різними функціями: пасажир купує квитки й переглядає власні поїздки, адміністратор розкладу керує потягами та переглядає їхнє навантаження, а провідник перевіряє квитки під час посадки. У початковій сутності `users` не було атрибута, який би визначав тип облікового запису.

**Розглянуті альтернативи:**
1. **Не зберігати тип облікового запису в моделі:** тип актора не був би видимим у схемі даних.
2. **Створити окремі сутності облікових записів для пасажира, адміністратора й провідника:** спільні дані користувача довелося б дублювати.
3. **Додати роль до `users`:** зберігати тип облікового запису в одному атрибуті спільної сутності.

**Прийняте рішення:**  
Додати до сутності `users` один атрибут `role` типу `enum` зі значеннями `PASSENGER`, `ADMIN`, `CONDUCTOR`. Це поле визначає тип облікового запису, який відповідає ролі актора в системі. Атрибут відображено в `users` у `spec.md` та `model.mmd`.

Сутність `passengers` залишається окремою: вона зберігає дані попутників, прив'язаних до користувача, а не ролі облікових записів. Пасажир, чиї дані внесено до квитка, не обов'язково має власний обліковий запис у `users`.

**Наслідки:**
- **Позитивні:**
  - Схема явно розрізняє типи облікових записів, потрібні для людських акторів системи.
  - Спільні дані облікового запису зберігаються в одній сутності `users`.
- **Обмеження:**
  - Одне поле `role` відображає один тип облікового запису для кожного користувача; підтримка кількох ролей для одного облікового запису моделлю не передбачена.
  - Перелік допустимих ролей у `enum` має залишатися узгодженим зі складом акторів EasyRail.
  - Модель визначає атрибут ролі, але не описує процес її призначення або правила перевірки доступу.
