# ADR 003: Застосування Snapshot Pattern для збереження квитків

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Сутність `Ticket_segment` містить зв'язки (FK) до користувача, станцій та рейсу. Система має забезпечувати формування електронного квитка (PDF) та вести історію подорожей в особистому кабінеті.

**Розглянуті альтернативи:**  
1. **Сувора нормалізація (Join Approach):** Зберігати у квитку лише ID (`user_id`, `station_id`). Для відображення імені пасажира чи назви станції робити JOIN із відповідними таблицями.
2. **Денормалізація / Snapshot Pattern:** Скопіювати критичні дані (ПІБ, назви станцій, розраховану ціну) безпосередньо в рядок `Ticket_segment` у момент успішної транзакції.

**Прийняте рішення:**  
Використовувати **Snapshot Pattern**. У специфікацію `Ticket_segment` навмисно додано поля-дублікати: `passenger_lastname`, `passenger_name`, `from_station_name`, `to_station_name`, `price`.

**Наслідки:**  
* **Позитивні:** Квиток стає незмінним юридично-фінансовим документом. Якщо адміністрація залізниці перейменує станцію, або пасажир змінить прізвище у своєму профілі — усі його архівні квитки залишаться незмінними і відображатимуть ті дані, які були актуальні на момент поїздки.
* **Негативні:** Локальне дублювання даних, що суперечить класичним правилам нормалізації, проте є архітектурно правильним для логіки фінансових документів.
