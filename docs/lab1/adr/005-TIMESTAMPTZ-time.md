# ADR 005: Виключне використання `TIMESTAMPTZ` (UTC) для часових міток

**Статус:** Затверджено  
**Дата:** Жовтень 2026  
**Контекст:**  
Поїзди курсують за графіком, перетинають різні часові зони, а пасажири можуть купувати квитки з будь-якої точки світу. Збереження часу в локальних форматах спричиняє критичні помилки під час переведення годинників (літній/зимовий час) або при порівнянні часу відправлення з `NOW()`.

**Розглянуті альтернативи:**  
1. **`TIMESTAMP WITHOUT TIME ZONE`:**  
   Зберігає абстрактну дату й час без інформації про зміщення. При перенесенні бази на інший сервер або зміні системного часу контейнера всі графіки рейсів зміщуються.
2. **Збереження Unix Timestamp (`BIGINT` у мілісекундах):**  
   Універсальний числовий формат, проте він унеможливлює використання нативних функцій PostgreSQL для інтервальної арифметики (`NOW() + INTERVAL '10 minutes'`, `EXTRACT(EPOCH FROM ...)`).
3. **`TIMESTAMP WITH TIME ZONE` (`TIMESTAMPTZ`):**  
   PostgreSQL внутрішньо завжди нормалізує значення в абсолютний час UTC, а при запиті повертає зміщення часового поясу.

**Прийняте рішення:**  
Усі поля дат і часу в системі (`departure_time`, `arrival_time`, `hold_expires_at`, `created_at`) оголошуються виключно як **`TIMESTAMPTZ`**. Усі розрахунки та сервіси бекенду працюють у єдиному часовому просторі **UTC**.

**Наслідки:**  
- **Позитивні:** Стійкість до сезонного переведення годинників. Коректна інтервальна математика на рівні БД (перевірка правила 2 годин до рейсу: `departure_time - NOW() >= INTERVAL '2 hours'`).
- **Негативні:** Клієнтська частина зобов'язана самостійно транслювати UTC-час у локальний час відповідної станції перед рендерингом для користувача.
