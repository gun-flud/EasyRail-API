# Промпт 6. Комплексне доопрацювання лабораторної роботи

## Контекст

Переглянь поточний `spec.md` повністю. Я вніс у нього зміни, тому орієнтуйся на актуальний файл, а не на попередні версії чи припущення.

У вимогах лабораторної позначено ✅ ті частини, результат яких мене влаштовує: актори й головні цілі, EARS-вимоги, User Stories, Gherkin і Use Case-діаграма. Інші частини потрібно перевірити й покращити відповідно до побажань нижче. Не змінюй без потреби вміст, який уже позначений як прийнятний.

## Завдання

### 1. EARS-вимоги

- Збережи наявний зміст вимог, але покращи оформлення, щоб було легко розрізняти типи EARS і їхню структуру: `WHEN`, `WHILE`, `IF ... THEN`, `WHERE` та універсальні вимоги.
- Перевір нумерацію, однозначність формулювань і послідовність термінів.
- Переглянь нефункціональні вимоги продуктивності. Додай вимірювані цілі часу відповіді для визначеного навантаження лише якщо вони обґрунтовані матеріалами проєкту.
- Не видавай припущення за затверджені вимоги. Якщо поріг навантаження чи швидкодії треба запропонувати, познач його як попереднє припущення для погодження або як непокриту вимогу.
- Не додавай Nginx чи іншу інфраструктуру як обов'язкове рішення без підтвердження в матеріалах. За потреби вкажи масштабування/інфраструктурне рішення як окреме питання або непокриту вимогу.

### 2. Gherkin-сценарії

- Зроби сценарії легшими для читання: розбий їх на окремі `Feature` за самостійними процесами, а не об'єднуй всю поведінку системи в одну функцію.
- Передбач окремі Feature для основних процесів, зокрема купівлі квитка, історії поїздок, створення рейсів воркером і сповіщень.
- Розмежуй дії актора, системи та зовнішнього сервісу; для альтернативних результатів оформи окремі сценарії.
- Використовуй англійські ключові слова Gherkin (`Feature`, `Scenario`, `Given`, `When`, `Then`, `And`, `But`), а описи кроків пиши українською.
- Не змінюй бізнес-правила й не додавай непідтверджену поведінку.

### 3. Матриця трасування

- Перевір матрицю на повноту, читабельність і відповідність фактичним ID вимог, Use Cases та сценаріїв у документі.
- Покажи зв'язки багато-до-багатьох: одна вимога може покриватися кількома Use Cases, а один Use Case — підтримувати кілька вимог.
- Познач непокриті й частково покриті вимоги або Use Cases явно. Не заявляй повне покриття, якщо артефакт перевіряє лише частину поведінки.
- Якщо матриця завелика, обери компактний Markdown-формат без надмірно широкої таблиці, але збережи всі зв'язки.

### 4. Аудит і узгодженість

- Перевір EARS-вимоги на двозначність.
- Перевір доречність зв'язків `<<include>>` та `<<extend>>`.
- Звір акторів і сутності з моделлю даних лабораторної роботи 1.
- Наведи три найважливіші розбіжності між специфікацією та відповідними артефактами; не вигадуй розбіжності, яких немає.
- Переконайся, що вимоги, Use Cases, сценарії, діаграми, матриця та `DEFENSE.md` не суперечать одне одному.

### 5. `DEFENSE.md`

- Переглянь пояснення меж сценаріїв і доповни їх там, де вибір меж потребує обґрунтування.
- Збережи зрозуміле пояснення, чому процеси розділено на окремі Use Cases та Gherkin Feature.

## Правила роботи

- Спочатку перевір фактичний стан усіх пов'язаних файлів і врахуй мої поточні правки.
- Внось узгоджені зміни у відповідні артефакти, а не лише перефразовуй цей запит.
- Не перезаписуй і не скасовуй мої зміни, яких не стосується завдання.
- Якщо вимогу неможливо підтвердити наявними матеріалами, познач її як непокриту або таку, що потребує уточнення.

## Результат

Покращи потрібні документи та діаграми так, щоб вимоги були чіткими, покриття було простежуваним, а непокриті питання — помітними. Наприкінці коротко підсумуй змінені файли, ключові покращення та вимоги, які залишилися непокритими або потребують погодження.
