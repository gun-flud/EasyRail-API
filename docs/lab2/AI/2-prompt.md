# Промпт 2. Уточнення Use Cases та вимог

## Контекст

Потрібно доопрацювати `spec.md` та пов'язані з ним діаграми/Use Cases для EasyRail API.
Не намагайся описати в межах одного Use Case абсолютно всі можливості системи. Зосередься на чотирьох основних процесах нижче та покажи їх зрозуміло й послідовно.

## Що потрібно зробити

### 1. Розділити систему на чотири основні Use Cases

1. **Купівля квитка**
   - Покажи покрокові дії зареєстрованого користувача: пошук за датою та станціями, вибір поїзда, вагона й місця, тимчасове бронювання, введення даних пасажира та оплата.
   - Після вибору місця система створює холд на 10 хвилин.
   - Відобрази обидва результати холда:
     - **Гілка -1:** користувач не встигає завершити оформлення; холд спливає, а місце звільняється.
     - **Гілка -2:** користувач вводить дані та переходить до зовнішнього платіжного процесу; після підтвердження оплати квиток фіксується, а дані пасажира й поїздки зберігаються у квитку.

2. **Перегляд історії поїздок**
   - Користувач відкриває особистий кабінет і переглядає власні квитки та поїздки, зокрема придбані, скасовані й ті, що не були завершені.
   - Історія має містити лише дані цього користувача.

3. **Створення поїздок**
   - Адміністратор вводить назву потяга та основні дані, необхідні для формування поїздок.
   - Система автоматично створює поїздки (`trips`) за 14 днів до дати їх проведення, щоб відкрити можливість бронювання місць.
   - Відокрем дії адміністратора від автоматичної роботи системного воркера.

4. **Надсилання сповіщень**
   - Система знаходить квитки, для яких до прибуття поїзда на станцію посадки пасажира залишається 2 години.
   - Система позначає такі квитки для сповіщення та надсилає пасажиру повідомлення: «На вашу зупинку прийде потяг через 2 години».

### 2. Узгодити вимоги, Use Cases і сценарії

- Для кожного Use Case визнач чіткі вимоги, які він реалізує.
- Use Cases мають доповнювати вимоги: кожна вимога повинна мати відповідне покриття Use Case, а кожен Use Case — бути пов'язаний із відповідними вимогами.
- Не додавай вимоги чи поведінку, що суперечать наявному змісту `spec.md` та моделі даних.
- Позначай непокриті або частково покриті вимоги явно — не заявляй повне покриття без підстав.

### 3. Оформити Gherkin-сценарії

- Використовуй англійські ключові слова Gherkin: `Feature`, `Background`, `Scenario`, `Given`, `When`, `Then`, `And`, `But`.
- Текст опису сценаріїв залишай українською.
- Кожен сценарій має описувати конкретну поведінку системи та очікуваний результат.
- Для основних гілок процесу купівлі квитка передбач окремі сценарії, зокрема успішну оплату та завершення холда за таймаутом.

### 4. Додати компактну матрицю трасування

Створи Markdown-таблицю, яка показує зв'язок між Use Cases та вимогами. Не використовуй надмірно широку матрицю з багатьма текстовими колонками.

| Use Case | ID вимоги | Покриття |
| :--- | :--- | :---: |
| UC-01 — Купівля квитка | REQ-... | X |

- Додавай окремий рядок для кожної пари «Use Case — вимога».
- Позначай `X` лише там, де Use Case справді покриває вимогу.
- Перевір, щоб усі ID вимог і Use Cases у таблиці існували в документі та були узгоджені між собою.

## Результат

Онови відповідні розділи `spec.md` і пов'язані діаграми/артефакти так, щоб чотири процеси були чітко розмежовані, сценарії читалися послідовно, а вимоги, Use Cases і матриця трасування не суперечили одне одному.
