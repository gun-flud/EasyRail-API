# DEFENSE — Завдання 2: Вимоги та Use Cases

### Намір і критерії (1–2 речення):

Метою є Формалізувати логіку EasyRail (EARS, Gherkin, Use Case) і чітко розмежувати ролі Користувача, Воркера та Платіжного шлюзу.
Має бути 100% покриття критичних шляхів (пошук → холд → оплата → повернення) у матриці трасування, крім однієї заздалегідь позначеної NFR.

Наміром є:
1. створення EARS-вимог (WHEN <тригер>, система SHALL <реакція> / WHILE <стан>, …) 
2. написання user stories 
3. написання Gherkin-сценаріїв (Given/When/Then)
4. створення матриці трасування для передбачення усіх сценаріїв, які буде покривати наші вимоги в форматі таблиці в Markdown.

---

### Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:

* **Контракт даних та типізація ключів:** 
  Концептуальні `UUIDv7` та `timestamptz` у вимогах суперечили фізичним `INT` identity та `DATE/TIME` у базовому SQL.  
  *Виправлення:* специфікацію жорстко прив'язано до стандартів ADR 002 та ADR 005 для забезпечення горизонтального шардингу. 


* **Розширення схеми квитка під Snapshot:** 
  Початкова концепція посилалася лише на зовнішні ключі, що призводило до втрати історичної цілісності фінансового документа.  
  *Виправлення:* специфікація явно вводить незмінний Snapshot (ПІБ, станції, ціна) безпосередньо в таблицю `ticket_segment`.


* **Часова семантика та ліміти продуктивності:** 
  Була невизначеність щодо відліку часу для сповіщень та повернень.  
  *Виправлення:* у вимогах формалізовано, що розрахунки ($\ge 2$ год для повернення, $\le 2$ год для сповіщень) ведуться виключно від `departure_time` станції посадки пасажира.


### Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):

**Реалізація Soft Delete через скінченну кількість станів**
* **Альтернативи:** 1) Додати булевий прапорець `is_deleted`. 2) Додати колонку `deleted_at`. 3) Використати існуючу систему статусів.
* **Прийняте рішення:** Формалізувати Soft Delete (REQ-EARS-UB-04) через термінальні стани `CANCELLED` та `EXPIRED` із фіксацією часу `cancelled_time`.
* **Чому обрав:** Це усуває потребу в додаткових прапорцях `is_deleted` та дозволяє зберігати повну історію квитків для архіву користувача без порушення унікальних індексів.

### Перевірка — узгодженість із попередньою моделлю (як перевірив):

Перевірку здійснено шляхом аудиту однозначності EARS та зв'язків Use Case із сутностями БД (`docs/lab1/model.mmd`):
* **Аудит БД:** Перевірено наявність полів для Snapshot (`passenger_name`, `from_station_name`, `price`) у `ticket_segment`.
* **Аудит Use Case:** Відношення `<<include>>` (перевірка інтервалів, ліміту холдів) та `<<extend>>` (автозбереження попутника `passengers`) логічно відповідають кардинальностям ER-діаграми.
* **Аудит EARS:** Перевірено використання вимірюваних констант (тайм-аут рівно 10 хв, фінанси в `INT` копійках), що повністю відповідає типам даних попередньої моделі.
