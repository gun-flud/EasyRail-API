# DEFENSE — Завдання 2: Вимоги, сценарії використання та трасування

### 1. Намір і критерії (1–2 речення):
Метою є Формалізувати логіку EasyRail (EARS, Gherkin, Use Case) і чітко розмежувати ролі Користувача, Воркера та Платіжного шлюзу.
Має бути 100% покриття критичних шляхів (пошук → холд → оплата → повернення) у матриці трасування, крім однієї заздалегідь позначеної. 

Наміром є:
1. створення EARS-вимог (WHEN <тригер>, система SHALL <реакція> / WHILE <стан>, …) 
2. написання user stories 
3. написання Gherkin-сценаріїв (Given/When/Then)
4. створення матриці трасування для передбачення усіх сценаріїв, які буде покривати наші вимоги в форматі таблиці в Markdown.
5. Виправлення моделей adr або erd , аби задовільнити усі необхідні критерії, які розписали протягом даної роботи

### 2. Топ-3 розбіжності (модель Завдання 1 ↔ spec Завдання 2 ↔ артефакти) + коміт-виправлення:

* **Розбіжність 1 (Життєвий цикл холда: ручна відмова в кабінеті vs таймаут воркера):**  
  *Суть розбіжності:* У Завданні 1 (ADR 007) перехід `HELD -> EXPIRED` розглядавався виключно як результат 10-хвилинного таймауту фоновим воркером. Сценарій, коли пасажир сам натискає «Відмовитися від броні» в особистому кабінеті, був не формалізований у станах квитка.  
  *Виправлення:* У `spec.md` та Use Cases (`UC-17`) закріплено, що добровільна відмова користувача від холда в кабінеті негайно переводить квиток у статус `EXPIRED` та вивільняє сегмент місця, усуваючи штучне 10-хвилинне блокування крісла та не змішуючи цей стан із `CANCELLED` (який закріплено за поверненням оплачених квитків). Рішення деталізовано та закріплено в новому **ADR 009** (`adr/009-manual-hold-refusal-expired-status.md`).  
  *(Коміт: `refactor(spec): formalize manual hold refusal as EXPIRED transition in user cabinet (ADR 009)`)*

* **Розбіжність 2 (Рольова модель):**  
  *Суть розбіжності:* На Use Case діаграмі з'явилися нові людські актори Адміністратор розкладу та Провідник, проте в таблиці users з Лаб 1 були лише пасажири   
  *Виправлення:* У специфікацію бази даних додано атрибут role (enum: PASSENGER, ADMIN, CONDUCTOR) для розмежування доступів до різних модулів.   
  *(Коміт: `fix(lab2): sync ER model, spec, readme with new ADRs 010 and 011`)*

* **Розбіжність 3 (Ідентифікатор транзакції):**  
  *Суть розбіжності:* Gherkin-сценарій успішної оплати та повернення вимагав взаємодії із зовнішнім актором `Payment Process`. Для реверсу коштів потрібен був номер банківської транзакції, якого не було в моделі.    
  *Виправлення:* Додано поле payment_transaction_id у таблицю `ticket_segment`   
  *(Коміт: `fix(lab2): sync ER model, spec, readme with new ADRs 010 and 011`)*

### 3. Ключове рішення — які альтернативи зважив і чому обрав цю (ADR) + Межі сценаріїв:

* **Межі сценаріїв (System Scope — In-Scope vs Out-of-Scope):**  
  - *В межах ядра (In-Scope v1):* Усі операції, критичні для цілісності інвентарю місць: пошук з інтервальною перевіркою, віртуальні місця (Lazy Evaluation, ADR 002), 10-хвилинний холд, оплата зі Snapshot (ADR 003), ізольований кабінет користувача, кабінет адміна з аналітикою навантаження потягів, автогенерація рейсів за 14 днів, сповіщення за 2 години та валідація посадки провідником.  
  - *Поза межами ядра (Out-of-Scope — Непокриті вимоги `[OUT]`):*  
    1. **REQ-EARS-UNC-01 (Фіскалізація чеків через ПРРО):** Зовнішній шлюз ДПС має високу латентність і жорсткі ліміти RPS; синхронний виклик під час пікових продажів заблокував би пул Fastify. Вимогу винесено в реліз v2 як асинхронний Outbox-сервіс.  
    2. **REQ-NFR-PERF-03 (Nginx L7 Rate Limiting / Virtual Waiting Room):** Черга очікування при напливі понад 10 000 користувачів належить до інфраструктурного рівня зворотного проксі, а не до коду бізнес-домену додатка.
  - *Чому платіжні шлюзи та воркери змодельовані як окремі актори:* Платіжний процес (LiqPay/Monobank) є зовнішньою системою з ізольованою зоною відповідальності за стандартом PCI DSS. Фонові воркери є системними акторами, які діють як автономні джерела подій (таймери cron без оператора).

### Перевірка — узгодженість із попередньою моделлю (як перевірив):

1. **Ланцюг моделей (Дані $\to$ Вимоги $\to$ Прецеденти):**  
   Перевірку здійснено шляхом аудиту однозначності EARS та зв'язків Use Case із сутностями БД (`docs/lab1/model.mmd`), усі 10 сутностей (`stations`, `stops`, `routes`, `trips`, `carriages`, `carriage_type`, `seat_templates`, `ticket_segment`, `users`, `passengers`) безпосередньо задіяні в прецедентах та трасуються в 2D матриці.

2. **Повне покриття всіх 8 ADR Завдання 1:**  
   - ADR 001 (монотонний `stop_order`) $\to$ `REQ-EARS-UB-03`, `UC-06`;  
   - ADR 002 (Lazy Evaluation місць) $\to$ `REQ-EARS-ST-01`, `UC-04`;  
   - ADR 003 (Ticket Snapshot Pattern) $\to$ `REQ-EARS-EV-02`, `UC-14`;  
   - ADR 004 (уніфіковані `UUIDv7`) $\to$ `REQ-EARS-UB-05`;  
   - ADR 005 (`timestamptz` UTC) $\to$ `REQ-EARS-UB-02`;  
   - ADR 006 (Soft Delete станів) $\to$ `REQ-EARS-UB-04`, `UC-09, 17, 18, 20`;  
   - ADR 007 (`FOR UPDATE SKIP LOCKED`) $\to$ `REQ-EARS-UW-01`, `UC-09`;  
   - ADR 008 (цілі копійки `int`) $\to$ `REQ-EARS-UB-01`.  
   Жодна вимога Завдання 2 не порушує контрактів концептуальної моделі даних Завдання 1.

3. **Аудит Use Case:** Відношення `<<include>>` (перевірка інтервалів, ліміту холдів) та `<<extend>>` (автозбереження попутника `passengers`) логічно відповідають кардинальностям ER-діаграми.

4. **Аудит EARS:** Перевірено використання вимірюваних констант (тайм-аут рівно 10 хв, фінанси в `INT` копійках), що повністю відповідає типам даних попередньої моделі.
